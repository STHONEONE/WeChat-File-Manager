# 微信文件管理器 V1.2 开发方案

**项目名称：** WeChat File Manager

**目标版本：** V1.2.0

**版本主题：** 智能扫描、重复文件检测与文件管理增强

**开发基础：** V1.1 已合并的稳定代码

**开发平台：** Windows 11，兼容性设计覆盖 Windows 10

**开发方式：** 集中完成多个功能，统一测试、验收和 GitHub 提交

**GitHub 仓库：** https://github.com/STHONEONE/WeChat-File-Manager

---

## 一、项目现状与版本定位

### 1.1 V1.1 已完成的基础

目前软件已经实现微信目录识别、多账号文件索引、中文目录管理、文件搜索、备注收藏、标签管理以及安全复制功能。

V1.1 进一步完成了搜索分页、目录按需加载、后台图片预览和 SQLite 数据恢复等功能。现有测试包含 22 项自动化测试，并对 50,000 条模拟索引进行了查询性能验证。

这些功能构成了 V1.2 的开发基础。本轮不再重复开发已有功能，而是在现有架构上增加智能管理能力。

### 1.2 V1.2 核心目标

V1.2 主要解决以下问题：

1. 用户无法快速判断微信目录中有哪些重复文件。
2. 文件索引更新仍依赖重新遍历目录，自动化程度不足。
3. 新接收文件后，需要等待扫描才能在软件中看到。
4. 文件统计信息相对基础，缺少直观的存储空间分析。
5. 批量处理能力仍有提升空间。

本轮完成后，软件应能够自动跟踪微信文件变化，识别重复内容，并让用户更方便地管理大量文件。

## 二、核心功能设计

### 2.1 重复文件检测系统（P0）

这是 V1.2 的重点新增功能。

软件增加独立的“重复文件”管理入口，用于识别微信目录中内容完全相同的文件。

检测采用分级策略：

**第一层：文件大小筛选。** 首先按照文件大小分组。只有大小相同且至少存在两个文件的分组，才需要进一步检查。

**第二层：内容校验。** 对候选文件计算 SHA-256 哈希值，确认文件内容是否一致。不同路径、不同名称但哈希值相同的文件，归入同一重复组。

**第三层：结果展示。** 将重复文件按组展示，显示文件名、账号、存储路径、文件大小和重复数量。

主要交互包括：

- 查看全部重复文件组。
- 按重复数量或总大小排序。
- 查看跨账号的重复文件。
- 打开任意重复文件及所在目录。
- 选择重复组中的文件进行复制归档。
- 显示重复文件的理论冗余容量。

哈希计算采用后台任务执行，并缓存已验证文件的哈希值。下次检测时，只有符合重新验证条件的文件才重新计算。

对于正在写入或发生变化的文件，应延迟检测或跳过，不能把不稳定的计算结果保存为有效哈希。

**安全要求：** V1.2 只检测和展示重复文件，不自动清理、删除或移动微信原文件。

### 2.2 智能增量扫描（P0）

优化现有扫描机制，减少重复读取和不必要的数据库更新。

主要方案是维护文件元数据快照，记录路径、文件大小、修改时间及可用的文件身份信息。

后续扫描时：

- 新文件：建立索引。
- 已修改文件：更新元数据并使旧哈希失效。
- 未变化文件：尽可能复用已有索引及哈希。
- 已删除文件：标记为不存在。
- 无法访问的目录：保留原有状态并提示异常。

需要区分目录遍历和内容计算。即使文件未变化，为保证文件增删检测的正确性，定期完整扫描仍可能需要遍历目录；优化重点是减少无意义的数据库写入、文件内容读取和重复统计。

继续保留手动完整扫描功能，防止自动监控遗漏文件变化。

### 2.3 自动文件监控（P0）

增加微信目录自动监控能力，使软件能够在运行过程中发现新增、修改和删除的文件。

监控采用 Windows 文件系统事件机制，可以优先评估 `watchdog`，在不适合监控的环境中回退到手动扫描。

具体功能如下：

- 可以在设置中开启或关闭自动监控。
- 检测到新增文件后，将其纳入索引。
- 检测到文件修改或删除后，更新对应记录。
- 多个连续文件事件合并处理，避免频繁刷新界面。
- 扫描和监控任务出现异常时，提供状态提示。
- 监控中断后支持重新启动，并通过完整扫描校正索引。

程序启动时可以恢复上一次的监控开关状态，但不能假设文件系统监控能够永久无遗漏运行。

为了降低系统资源占用，需要对文件事件进行防抖和批量处理，避免微信大量接收文件时造成界面卡顿。

### 2.4 批量文件操作增强（P1）

在 V1.1 已有的多选复制基础上，进一步完善批量管理功能。

新增支持：

- 为多个文件批量添加标签。
- 为多个文件批量移除指定标签。
- 批量收藏或取消收藏。
- 对筛选结果执行批量操作。
- 操作完成后保留合理的列表位置和筛选条件。

批量操作前应明确展示选中文件数量，执行后反馈成功数量、失败数量及失败原因。

批量标签操作只修改软件自身的 SQLite 数据，不影响文件内容和真实路径。

### 2.5 存储空间统计增强（P1）

将现有的简单统计对话框升级为独立统计界面。

统计内容包括：

**文件分类统计：** 展示文档、图片、视频、音频及压缩文件的数量和存储空间占比。

**微信账号统计：** 对比不同账号的文件数量和占用空间。

**大文件排行：** 支持按文件大小排序，快速查看占空间较多的文件。

**重复文件统计：** 展示重复组数量、重复文件数量以及理论冗余容量。

**目录空间分布：** 基于已扫描的文件元数据，展示主要目录的存储占用情况。

界面建议采用简洁的统计卡片、条形图和数据列表，不需要引入复杂的数据可视化框架。

统计数据应注明扫描时间。对于未完成扫描、无法访问的目录和未完成哈希检测的文件，不能将不完整数据展示为完整结果。

## 三、软件界面调整

V1.2 继续沿用 Windows 文件资源管理器式布局，不重新设计整个软件。

### 3.1 左侧导航栏

建议调整为以下结构：

```text
微信文件管理器
│
├── 全部文件
├── 最近文件
├── 收藏文件
│
├── 智能管理
│   ├── 重复文件
│   ├── 大文件
│   └── 存储统计
│
├── 文件分类
│   ├── 文档
│   ├── 图片
│   ├── 视频
│   ├── 音频
│   └── 压缩文件
│
├── 我的标签
│
└── 微信账号
    ├── 账号一
    └── 账号二
```

### 3.2 重复文件页面

中央区域采用重复组列表。

选择某个重复组后，显示该组内各文件的路径、名称、时间和所属账号，方便判断它们是否来自不同位置。

提供“打开文件”“定位文件”“复制路径”等操作。

### 3.3 统计页面

顶部展示文件总数、总占用空间、重复组数量及已确认的理论冗余容量。

下方展示文件类别分布和大文件排行。

### 3.4 扫描状态显示

在软件底部状态栏显示当前扫描或监控状态。

支持展示扫描中、监控中、空闲和异常等状态，以及最近一次成功扫描的时间。

新增功能需要保持现有界面的一致性，避免在主窗口中堆积大量按钮。

## 四、技术架构与数据库设计

### 4.1 技术选型

继续使用现有技术体系：

| 技术 | 主要用途 |
|---|---|
| Python | 核心业务逻辑 |
| PySide6 | Windows 图形界面 |
| SQLite | 文件索引与用户数据 |
| SHA-256 | 重复文件内容校验 |
| watchdog（待评估） | 文件系统变化监控 |
| QThread / 后台任务 | 扫描、哈希计算与预览 |
| pytest | 功能与回归测试 |

原则上不增加大型第三方依赖，仅在现有技术无法合理实现功能时引入新依赖。

### 4.2 代码结构调整

在 V1.1 现有模块基础上，增加独立的重复文件检测和文件监控服务。

建议模块包括：

```text
app/
├── core.py
├── database.py
├── scanner.py
├── duplicate_detector.py
├── file_monitor.py
├── statistics.py
└── ui/
    ├── window.py
    ├── duplicates.py
    ├── statistics_view.py
    └── components/
```

这是目标逻辑结构，不要求为了达到该结构而重写全部旧代码。

优先采用渐进式重构，保留 V1.1 现有接口及功能。

### 4.3 数据库扩展

为 V1.2 增加必要的索引和哈希缓存字段或独立表。

需要保存的信息包括：

- 文件规范化路径及现有身份信息。
- 上次哈希计算对应的文件大小、修改时间和文件身份。
- SHA-256 结果及校验状态。
- 最近一次成功验证时间。
- 扫描状态与监控设置。

重复组可以依据有效哈希动态查询，不一定需要长期维护重复的分组数据。

所有数据库结构变化必须通过版本迁移完成。升级前应保留备份，确保原有备注、收藏和标签不丢失。

## 五、性能优化与资源管理

### 5.1 文件哈希计算

重复文件检测可能读取大量文件，因此不应一次性为全部文件计算 SHA-256。

优先使用文件大小过滤候选，并采用流式读取，避免将完整大文件加载到内存中。

后台哈希任务应支持取消，同时限制并发数量，避免持续占满磁盘带宽。

### 5.2 扫描与数据库写入

扫描结果分批处理，减少重复 SQL 操作。必要时使用事务批量提交，降低数据库写入开销。

扫描过程中不能阻塞主界面，也不能在取消时产生不一致的部分状态。

### 5.3 文件监控

高频文件事件应先进入待处理队列，再合并执行索引更新。

对频繁变动的大文件采用延迟检查机制，避免文件尚未写入完成就重复读取。

监控积压、事件丢失或监控根目录发生异常时，应通过重新扫描恢复一致性。

## 六、安全与隐私要求

V1.2 延续之前版本的文件安全设计。

1. 微信原始目录仍然只读，不提供源文件删除、移动或重命名功能。
2. 哈希检测只读取文件内容，不修改文件。
3. 不解密微信数据库或专有加密附件。
4. 不上传文件内容、路径、哈希及用户备注至服务器。
5. 监控异常或文件访问失败时不能自动删除索引中的用户备注。
6. 数据库迁移必须保留原有用户数据。
7. 所有复制导出操作继续执行源目录保护与结果校验。

对于重复文件统计，应将理论冗余容量与实际可释放空间区分开来，避免让用户误认为这些空间可以直接安全清理。

## 七、开发实施安排

本轮采用集中开发方式，不要求每个模块完成后都进行一次完整测试和 GitHub 提交。

### 第一部分：核心能力建设

集中实现重复文件检测、哈希缓存、扫描优化及自动监控机制。

完成核心数据结构和后台任务管理。

### 第二部分：界面和交互完善

实现重复文件页面、文件统计界面、批量操作以及监控状态展示。

保持整体界面统一，复用现有文件列表、标签和搜索能力。

### 第三部分：集中测试与修复

所有主要功能集成后，统一运行自动化测试、性能测试和必要的 Windows 原生界面测试。

对于数据库迁移、源目录保护等高风险功能，允许开发期间进行针对性的快速检查，避免严重问题累积。

发现问题后集中修复，再运行相关回归测试。

### 第四部分：统一提交

更新 README、开发方案、测试报告和版本记录。

完成测试并确认无阻断问题后，将整轮 V1.2 改动统一合并至 GitHub main 分支。

不制作正式安装包，不创建 GitHub Release，也不要求发布 ZIP。

## 八、V1.2 验收标准

### 8.1 功能验收

| 验收项目 | 通过标准 |
|---|---|
| 重复文件检测 | 不同名称但内容相同的文件能够被正确分组 |
| 哈希缓存 | 未变化文件可复用有效哈希，修改后能重新验证 |
| 增量扫描 | 新增、修改、删除能够正确更新索引 |
| 自动监控 | 文件变化后可自动更新，监控失败可恢复 |
| 批量管理 | 批量标签和收藏正确保存 |
| 文件统计 | 分类、账号、大文件和重复统计结果准确 |
| 数据兼容 | V1.1 个人备注及设置升级后保持完整 |
| 文件安全 | 不修改微信原始文件 |

### 8.2 性能验收

沿用 V1.1 的测试基础，继续使用至少 50,000 条模拟文件索引验证查询及列表性能。

重复文件检测使用包含相同内容、不同文件名、空文件、大文件及扫描期间发生变化的模拟数据集。

记录首次检测耗时、重复检测耗时、哈希缓存命中率及监控触发后的索引更新时间。

扫描优化应对比 V1.1 的实际基准结果，而不是仅与理论预期比较。

运行过程中应确保界面保持响应，长时间任务可以取消。

### 8.3 兼容性验收

以 Windows 11 为主要实测平台。Windows 10 在具备测试环境之前继续标记为待验证。

保留 V1.1 原有自动化测试，并为新增功能补充测试。

不能仅根据 Windows Server CI 通过就宣布 Windows 10 桌面兼容性已经验证。

## 九、V1.2 暂不实现的功能

本轮不加入以下能力：

- 微信聊天记录数据库解密。
- 自动识别附件来源的联系人或聊天群。
- PDF、Word 等文档正文全文搜索。
- AI 文件分类与语义检索。
- 自动删除重复文件。
- 直接清理微信缓存及聊天数据库。
- 云同步或跨设备同步。

上述功能留待未来版本单独规划。

## 十、交付成果与完成条件

本轮开发需要形成以下成果：

1. 完整的 V1.2 源代码。
2. 重复文件检测与自动监控功能。
3. 增强后的文件统计和批量管理界面。
4. 数据库迁移及兼容性处理。
5. 自动化测试、性能测试和测试报告。
6. 更新后的 README 与开发文档。
7. 合并到 GitHub main 分支的统一开发提交。

V1.2 完成后不立即发布正式软件，而是继续根据实际使用情况进入后续版本开发。

**版本完成标准：能够稳定实现自动索引更新、重复文件分析和批量管理，同时保持 V1.1 的所有既有功能与数据安全性。**

最终目标是让微信文件管理器从一个以搜索为主的工具，逐步发展为能够主动维护索引、分析文件状态并提供高效管理能力的本地桌面软件。
